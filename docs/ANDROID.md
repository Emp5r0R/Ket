# Android data plane

Ket Android consumes the versioned control API directly and implements platform-owned Hysteria2, Hysteria XOR, VLESS + REALITY, XHTTP/TLS Stealth, Shadowsocks 2022, WireGuard TLS, and OpenVPN/stunnel choices. Hysteria XOR reuses the maintained Hysteria engine with strict Salamander/Gecko validation. It does not run the desktop broker or attempt desktop-style privileged route changes.

OpenVPN uses a maintained Android PIE executable as a separate process. Ket implements the private Unix management protocol itself, retains `VpnService` route ownership, and passes a duplicate TUN descriptor to OpenVPN with `SCM_RIGHTS`. Ket's certificate-pinned Java TLS carrier is compatible with the server-side stunnel listener, so Android does not bundle or launch the desktop stunnel program.

## Packet path

1. The user pastes an invite, scans its QR code with the camera, or opens a QR image (Advanced still accepts a server URL and access code). The invite is verified locally before anything is sent, by the same Rust implementation the server and desktop use (`libket_invite_jni.so`, reached only through the `InviteReader` interface); its node key is pinned, and every enrollment for that profile must carry the node's signature. Camera access is requested only when scanning, the scanner window is `FLAG_SECURE`, and selected images are size-bounded and never uploaded. The UI then obtains Android VPN permission before exchanging the 32-character access code.
2. Control responses must use the exact endpoint status code, fit within 128 KiB, and decode as strict UTF-8 before JSON parsing. Enrollment requires a 44-character token and live lease; renewal and status must return the 12-character session ID encoded by that token, the exact Android client identity, a future lease, valid node data, and internally consistent traffic counters. Server error text is control-free and capped before it reaches the UI.
3. The validated manifest is ranked by server priority and the user's optional protocol preference. Android accepts at most 32 profiles with bounded unique identifiers and credentials: strict Hysteria2 UDP settings; VLESS + REALITY with Vision and validated public-key material; XHTTP `packet-up` with certificate-verified TLS and a bounded path; Shadowsocks 2022 with the exact SIP022 method and 32-byte key; WireGuard TLS with exact routes, address allocation, WebSocket carrier, and three 32-byte keys; or OpenVPN TCP with exact TLS/cipher policy, two bounded CA documents, `tls-crypt`, and a lease-scoped username/password. Node identity, country/city, coordinates, health, capacity, CPU, memory, uptime, and observation time are range-checked before entering UI state.
4. A successful manual enrollment atomically persists the normalized control endpoint, access grant, complete current session manifest, and optional protocol preference in an authenticated encrypted record. Changing the preference updates that record without consuming another access grant. An app launch is explicitly flagged; an unflagged system launch restores the current lease and preference for always-on VPN. Ket renews a saved session before use, replaces it only after confirmed authorization loss, and retains it optimistically when a restricted network blocks the control endpoint.
5. The service attempts each supported transport in rank order. Automatic mode may fall through from an unavailable upstream payload, failed OpenVPN TLS, WireGuard TLS, XHTTP/TLS, REALITY, Shadowsocks path check, or other retryable startup failure to the next ranked protocol. An explicit user selection filters the candidate set before ranking, so only matching endpoints can be retried during startup or recovery. Successful latency and failures feed a bounded exponential-cooldown history.
6. Hysteria starts in SOCKS5 TCP/UDP mode and sends its outbound QUIC descriptor over an abstract Unix socket. Ket receives it through `SCM_RIGHTS`, calls `VpnService.protect`, closes the duplicate, and acknowledges the engine.
7. Before installing a VPN route, Ket resolves each advertised data-plane endpoint and pins the selected engine to a numeric address. Xray starts with a loopback SOCKS inbound, validates its generated REALITY, XHTTP, or userspace WireGuard configuration, and proves the selected path with a certificate-verified request through SOCKS. WireGuard additionally starts `libwstunnel.so` with certificate verification, the public SNI/Host header, a strict WebSocket path, and loopback UDP forwarding. Shadowsocks starts `libsslocal.so` with an ephemeral strict TCP+UDP configuration and completes the same path test. The pinned endpoint or CDN addresses are excluded from the VPN to prevent recursion during startup and Automatic fallback. Explicit selections retry only matching protocol profiles.
8. Ket requires each SOCKS engine, including Hysteria, to carry a certificate-verified TLS handshake before it creates a VPN route. After that probe succeeds, Ket registers hev's bridge-local mapped DNS address with `VpnService.Builder`, never enables `allowBypass`, installs full routes, and passes the TUN descriptor to hev-socks5-tunnel with SOCKS UDP enabled. Mapped DNS returns short-lived synthetic IPv4 answers and restores the original domain in each SOCKS request, so the data-plane server chooses a reachable address instead of inheriting a client-preferred IPv6 address that an IPv4-only VPS cannot route. Ket rejects TCP sent to the UDP-only mapped resolver so Android Private DNS fails over immediately instead of proxying an unroutable synthetic address, then repeats the certificate-verified routed HTTPS gate once after resolver fallback. DNS remains inside the TUN. API 26-32 receive an exact CIDR complement for every excluded transport address; API 33 and newer use platform exclusion routes.
9. OpenVPN instead connects only to Ket's protected loopback TLS carrier. Its private management channel supplies the scoped credentials in memory, accepts bounded interface and DNS callbacks, rejects unknown operations, establishes the full-route Android TUN, and transfers a duplicate descriptor to the maintained OpenVPN process. Both the outer carrier certificate and inner OpenVPN certificate are hostname-verified against independent manifest CA material. Management byte counters feed the same UI telemetry contract.
10. Before publishing `Liberated`, the foreground service requires a certificate-verified HTTPS 204 response through the installed full-route TUN. A listener-only connection or server with no usable egress fails that candidate. Automatic mode continues bounded cross-protocol fallback; an explicit selection remains locked to matching profiles during startup and recovery. The service then owns renewal, traffic sampling, process and routed-path health, failure reporting, and session release. It observes only non-VPN internet networks, debounces Wi-Fi/mobile callback bursts, and checks the route after the available underlying network set changes or returns from an outage. Most engines open new connections over the new network on their own, so after 3 seconds Ket repeats the routed HTTPS check, and once more 2 seconds later; a route that still works is kept with nothing shown, and only a broken one enters recovery, trying the same transport first because the network rather than the transport was at fault. While no network exists Ket waits instead of recovering. HTTPS lease renewal traverses the active VPN and is independent of local bridge statistics. Ket ignores expected network suspension while Android reports Doze, then serializes an immediate renewal and status refresh when idle mode ends. Authorization loss stops immediately. Starting with the second ordinary control failure, Ket independently repeats the routed HTTPS check; a healthy route stays connected despite an unavailable control server, while a failed route enters bounded recovery.
11. If an established engine exits, both its routed control path and independent HTTPS health check fail, or the route stops working after a network change, Ket retains the lease and the last established TUN while it stops the old bridge and engine. That TUN keeps application and DNS traffic fail closed while ranked alternatives start. Android establishes the replacement TUN before Ket releases the previous descriptor, then Ket attaches the required SOCKS or native OpenVPN route. A failed attach leaves the newest TUN installed as the next guard. Recovery is bounded to three rounds and does not itself release the session.

Transport configurations are mode `0600` under `noBackupFilesDir` and are deleted after readiness. The hev configuration contains only loopback plumbing and is removed at shutdown. OpenVPN receives its profile over standard input and its scoped credentials over a mode-`0600` Unix management socket; neither is persisted. Credentials are never written to logs or exposed through state snapshots.

The durable record also lives under `noBackupFilesDir` and is written through `AtomicFile`. Its contents are sealed with AES-256-GCM and a non-exportable [Android Keystore](https://developer.android.com/privacy-and-security/keystore) key; credentials cannot migrate through Android backup without that device-local key. The first manual connection must succeed before enabling [always-on VPN](https://developer.android.com/develop/connectivity/vpn#always-on). Android can then start the foreground service after process death, reboot, or app upgrade, while system lockdown blocks traffic before Ket establishes its full route. The packaged manifest advertises always-on support, but the reboot and lockdown lifecycle remains a physical-device release gate.

The Compose surface uses the same node contract as desktop. The screens and the status island are described under [Screens](#screens). A valid encrypted profile is shown as a saved server and reused without asking for the code again; only its access expiry or the explicit **Forget** action removes it. The interface follows the system color scheme by default and provides persistent Light and Dark overrides while retaining Ket's red connected accent. It renders the bundled Natural Earth 1:110m topology as a neutral full-world view while disconnected, smoothly focuses on the active server region after end-to-end route verification, and returns to the full view during disconnect cleanup. Terminal connection failures open a copyable bounded diagnostic report covering enrollment, VPN permission, transport resolution/start, full-route verification, recovery, lease renewal, session release, credential cleanup, bridge, engine, and TUN cleanup. Codes, tokens, credentials, configurations, and raw process output never enter that report, and arbitrary messages receive a defensive redaction pass. The connect button sits within the first screenful on common phone sizes, and every screen scrolls under constrained height. The Natural Earth-derived asset and its redistribution notice are tracked with the Android source.

## Screens

The app has four tabs: Connect, Metrics, Protocols, and Settings. Each screen lives in its own package under `com.ket.android.ui`; `KetApp` owns navigation and state, and the screens only draw what they are given.

- **Add your server** (Connect, before a server is saved): **Paste invite** reads the clipboard, **Scan QR** opens the camera, and **From image** reads a QR picture. Advanced still takes a server address and access code. Errors appear under the buttons and say what to do next.
- **Share to Ket**: sharing text that contains a `ket:invite:` from another app (a chat, an email) opens Ket with the invite filled in. Ket shows the server it names and asks before adding it. If a server is already saved, Ket keeps it and explains how to switch: forget the current server in Settings, then share the invite again.
- **Connect**: the server's location, the map, the connect button, a route card (protocol, why Ket left another protocol), and a protocol row. The row opens a bottom sheet that lists Automatic and only the protocols the server offers; it is disabled while connecting or connected.
- **Metrics**: traffic, protocol, setup time, and access left for this connection, then the server's health, load, processor, memory, and uptime.
- **Protocols**: one card per protocol, the server's own first. A card opens to when to use it, how it works, how to connect, and its limits, with a button to choose it.
- **Settings**: theme (System, Light, Dark), apps that use Ket, connection options (including the protocols Automatic tries), the saved server with a confirmed **Forget**, help links, and the app version.

### Status island

A dark capsule at the top centre of every screen shows the connection state, like a phone's dynamic island:

- Off: a red dot pulses like a recording light with "You are being watched" or "You are under surveillance".
- Connecting, reconnecting, or stopping: a spinner and the current step.
- Connected: a green shield and "Liberated".
- Failed: a warning sign and the reason.

When the state changes the island opens for 3.5 seconds with a second line, such as "Protected with HTTPS Stealth", then folds back. A tap opens or closes it. On a dark theme it is lifted and outlined so it stays visible. It is a polite live region, so screen readers announce each change.

## Apps that use Ket

Settings, "Apps that use Ket", chooses between all apps (the default), only chosen apps, and all apps except chosen ones. The list shows apps with a launcher entry, through a manifest `<queries>` entry rather than broad package visibility. The choice is stored in ordinary app preferences and applied every time the VPN interface is built, including always-on starts after a reboot; changing it while connected takes effect on the next connection.

`SplitTunnelRules` turns the choice into `VpnService.Builder` rules:

- Android allows either an allow list or a deny list on one interface. Ket uses one or the other, never both.
- Ket itself is always inside the VPN. In "only chosen apps" it is added to the allow list, and it is never put on the deny list, because its routed-Internet check and lease renewals must travel through the tunnel they verify.
- Apps that are no longer installed are skipped. If none of the chosen apps is left, every app uses Ket, the protective default, and diagnostics record why.
- `allowBypass()` stays off, so apps inside the VPN cannot bind around it.

Apps outside the VPN reach the network directly, with no Ket protection and their own DNS. Under Android's "Block connections without VPN" (lockdown), apps outside the VPN have no network at all.

## Connection settings and fallback reasons

Settings, "Split the TLS greeting" (off by default), makes Xray send the ClientHello of VLESS + REALITY and HTTPS Stealth as 100-200 byte TLS records 10-20 ms apart, through a fragmenting dialer, so a filter that reads the server name from one packet misses it. It is read from ordinary app preferences each time a transport starts, so it also applies to always-on starts.

When Automatic mode leaves a protocol, or recovery replaces a lost one, the connection card lists each protocol it left with the reason ("Using HTTPS Stealth because: VLESS + REALITY: ..."). A fresh connection clears the list; a recovery keeps it, capped at eight entries. A chosen protocol that the invite no longer offers fails with a message naming it, instead of a generic startup failure.

## Native supply chain

`packaging/prepare-android-engines.sh` downloads checksum-pinned Hysteria 2.10 and OpenVPN for Android 0.7.64 executables/libraries for `armeabi-v7a`, `arm64-v8a`, `x86`, and `x86_64`, Xray-core 26.3.27 and shadowsocks-rust 1.24.0 for `arm64-v8a` and `x86_64`, and wstunnel 10.6.2 for `arm64-v8a`. It also verifies and expands the complete hev-socks5-tunnel 2.14.0 source release. NDK r27d compiles hev and Ket's small API-26-compatible FD receiver for every ABI. `packaging/build-android-invite.sh` builds Ket's invite verifier (`crates/ket-invite-android`, `libket_invite_jni.so`) from the workspace with the same NDK and 16 KB page alignment for every ABI, and a host copy for the JVM unit tests. The official Shadowsocks and wstunnel binaries target Android API 28; wstunnel is currently arm64-only. Unsupported devices retain ranked fallback rather than weakening a profile.

Generated third-party files live under `app/build/generated/ket-engines` and are not tracked. The APK validator requires Hysteria, OpenVPN, hev, the Ket JNI shim, and the Rust invite library for every ABI, Xray plus Shadowsocks for both supported 64-bit ABIs, and wstunnel for arm64 before CI uploads the artifact.

Gradle builds one APK per ABI plus a universal APK (`app-<abi>-<variant>.apk`, `app-universal-<variant>.apk`). Releases ship two of them: `Ket_<version>_android-arm64.apk` for current phones, about half the size of the universal one, and `Ket_<version>_android-universal.apk` for everything else. Both are signed with the same key and version, so either one updates the other. `validate-android-apk.sh --abi <abi>` requires a split to carry exactly its own ABI's engines; `--abi universal` (the default) requires all four ABIs.

The app's `versionName` and `versionCode` come from the workspace version in `Cargo.toml` (`versionCode` = MAJOR×10000 + MINOR×100 + PATCH). `KET_ANDROID_VERSION_NAME` and `KET_ANDROID_VERSION_CODE` still override them for test builds, but `build-android.sh release` refuses overrides that disagree with the workspace.

## Verification

```bash
./packaging/build-android.sh debug
GRADLE_USER_HOME=/media/n_emperor/Aadhish/gradle-home \
  apps/ket-android/gradlew --no-daemon testDebugUnitTest assembleDebug lintDebug
./packaging/validate-android-apk.sh --abi arm64-v8a \
  apps/ket-android/app/build/outputs/apk/debug/app-arm64-v8a-debug.apk
```

`./packaging/build-android.sh` defaults to `debug`; the explicit argument avoids confusing a test build with a release. A release build requires all signing variables and pins the resulting APK to the expected certificate:

```bash
export KET_ANDROID_KEYSTORE=/secure/path/ket-release.p12
export KET_ANDROID_KEYSTORE_PASSWORD='<keystore password>'
export KET_ANDROID_KEY_ALIAS=ket-release
export KET_ANDROID_KEY_PASSWORD='<key password>'
export KET_ANDROID_CERT_SHA256='<64-hex-digit certificate SHA-256>'
./packaging/build-android.sh release --out release-artifacts/v<version>
```

Obtain the expected fingerprint with `keytool -list -v -keystore "$KET_ANDROID_KEYSTORE" -alias "$KET_ANDROID_KEY_ALIAS"`; let `keytool` prompt for the password. Gradle rejects every release task when the signing environment is missing or partial. The wrapper then verifies both shipped APKs' signatures and requires their signer certificate to match `KET_ANDROID_CERT_SHA256` before copying them, under their release names, into the `--out` directory.

The debug APK is build evidence, not a production release. CI generates a short-lived signing identity to prove that the release variant, both shipped splits' native payloads, and certificate check work together, but it neither uploads those release APKs nor establishes a production signer. Unit tests cover bounded strict-UTF-8 control reads, token/status identity and lease binding, strict parsing for every maintained transport and Hysteria XOR mode, the complete node/status contract, OpenVPN profile hardening and credential isolation, authenticated credential-envelope tamper detection, durable session resume/re-enrollment decisions, orphan-session cleanup, the exact bundled world topology and coordinate projection, bridge-local mapped DNS configuration, routed-Internet probe fallback, SOCKS UDP forwarding, IPv4/IPv6 route inclusion and exclusion, fail-closed replacement-route ownership, Doze refresh gating, terminal authorization loss, deterministic recovery ranking/cooldown, underlying-network transition decisions, cooperative startup cancellation, and process-output shutdown races.

On 2026-07-19, the arm64 payload was exercised on a physical Android 16/API 36 device against the dual-transport Oracle ARM deployment. Both Hysteria2 and VLESS + REALITY established protected routes and reported nonzero bidirectional traffic. The device also proved automatic startup fallback, recovery after forcibly terminating the active Xray child while retaining its lease, cancellation with both data planes unreachable, lease release, and repeated crash-free disconnects. Temporary server firewall rules used for the unreachable-path test were removed and readiness was rechecked afterward.

On 2026-07-20, USB-controlled testing switched the same connected device from Wi-Fi to cellular and back. Ket retained its lease, changed the Android underlying network in both directions, recovered from VLESS + REALITY to Hysteria2 and back to VLESS + REALITY, and returned to a validated full-route VPN with the configured VPN DNS servers. Sampling also caught the VPN interface disappearing during the old cleanup sequence. The recovery implementation now retains an established TUN as a fail-closed guard and replaces it only after Android establishes the next interface; local unit, build, lint, signature, and APK payload checks pass, but this correction still requires a physical repeat.

On 2026-07-22, production logs from the IPv4-only Oracle node exposed the reason Android applications appeared connected without Internet: client DNS selected AAAA destinations, while Hysteria2 and Shadowsocks both reported `network is unreachable` for every IPv6 egress attempt. The mapped-DNS correction and pre-connected HTTPS gate then passed on the same restricted Wi-Fi network with an owner-signed API 36 arm64 APK and explicit VLESS + REALITY. Ket published `Liberated` only after end-to-end traffic, the device received `204` from the Google connectivity endpoint, and Cloudflare reported the Oracle egress address `161.118.195.126`. A repeated explicit run through the temporary direct TCP `8443` deployment produced the same Oracle egress, an Android `IS_VALIDATED` full-route VPN, TLS 1.3 through Cloudflare's Singapore edge, and UI counters of 7.1 MB received and 2.3 MB sent. Production now shares TCP `443` between HTTPS and REALITY through SNI prereading. Automatic Shadowsocks 2022 and explicit XHTTP/TLS Stealth also passed the routed gate on that restricted network. Disconnect removed the VPN network and restored direct egress `139.167.143.182`; the earlier disposable grant was revoked.

The v1.0 Android implementation scope is complete. Repeat the corrected switch test on the API 36 device, exercise Hysteria2, Hysteria XOR, OpenVPN TLS, and WireGuard TLS end-to-end on the restricted network, and run the Hysteria/OpenVPN compatibility matrix on a physical API 26 device as post-implementation release qualification. The implemented Doze-exit renewal, graceful VPN-permission revoke, process/reboot restoration, always-on/lockdown lifecycle, explicit connected-state DNS leak behavior, and owner-signed Windows installation remain physical-device gates in [the future-work register](FUTURE_WORK.md).
